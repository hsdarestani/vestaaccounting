# PostgreSQL source-data runtime

This is the actual Node HTTP runtime/adapter, with a dedicated PostgreSQL database, not a D1 or SQLite backing store. It reuses the tested accounting application handler and new UI. `MODE=source` has an explicit posting denylist-by-default: only draft journal/settings/reconciliation operations and synchronization requests are permitted. Raw WooCommerce revisions are independently append-only, with current pointers. The source database is not initialized with synthetic figures.

## Private provisioning gates

Use an isolated database and a private `.private.env`, never repository content. Set `DATABASE_URL`, `IP_SALT` and `MFA_REQUIRED=0`; the owner chose password-only login. For sync, configure `WOO_ORIGIN` and a dedicated read-only API key pair privately on the host. A webhook secret is optional. `IRANYEKAN_FONT_PATH` must point to a licensed WOFF2 mounted privately; otherwise use bundled Vazirmatn. `ADMIN` and `PASS` are injected into `node provision.mjs` only for first provisioning; only the scrypt hash is persisted. The upgrade workflow verifies the existing identity without resetting it and tests session security and CSRF after deployment.

Build with `docker build -f runtime/Dockerfile .`; use `runtime/compose.yml` only after capacity and backup checks. Apply `node migrate.mjs` against the new database before app/worker startup. Bind the HTTP port to loopback, add a dedicated authenticated HTTPS reverse-proxy route or isolated tunnel (no shared storefront restarts). Verify external HTTPS and the health endpoint (`database: postgresql`, `mode: source`, `posting_authorized: false`) before replacing the evaluation route. Existing demo database remains separate. Plan backup encrypted off-host, restore rehearsal and utilization monitoring before importing large batches.

The sync worker uses GET-only bounded pages, a persistent checkpoint, an advisory lock and scheduled incremental/periodic checks. A signed webhook only queues source evidence; it never writes WooCommerce or posts finance. Webhooks need explicit registration after the new HTTPS endpoint is externally reachable. Verify counts against source pagination; unknown stock and original currency remain raw. APIs and secrets are never included in logs or repo.

The Vesta origin uses a dedicated Nginx vhost and Cloudflare strict TLS. Preserve the accounting vhost when replacing the shared origin configuration; it opens no new external port. The demo Worker and demo database remain independent. The private source worker uses a dedicated WordPress reader and a read-only WooCommerce API key. The catalog adapter returns only mapped product fields to that reader; it is not accessible anonymously and does not add a write endpoint. Product and historical order data are independent of the ledger. Review exact counts and last complete sync in the authenticated integration view.
